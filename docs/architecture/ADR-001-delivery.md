# ADR-001: доставка сообщений и звонков в «Чё-Там»

- **Статус:** принято
- **Дата:** 2026-10-01
- **Область:** Android и будущий iOS-клиент; доставка сообщений, пробуждение приложения и сигнализация звонков.

## Контекст

Канарейка в мобильной сети показала: WebSocket без трафика закрывается через 9–15 минут, а с ping раз в 1–9 минут сохраняется. У родственников есть Android-устройства с Google Mobile Services (Xiaomi/Samsung) и iPhone. Постоянное Android-уведомление допустимо.

Нужно обеспечить доставку сообщений и звонков в условиях нестабильной/ограниченной сети, не создавая дублей и не завися от одного канала доставки.

## Решение

### 1. Пробуждение Android

Используются оба пути одновременно:

- срочный FCM push высокого приоритета;
- собственное WebSocket-соединение в foreground-службе с тихим постоянным уведомлением «Чё-Там на связи».

Сообщение и приглашение звонка отправляются по обоим путям. Дубликаты устраняются по стабильному `id`. Каждый срочный FCM push сопровождается обычным видимым уведомлением о сообщении или звонке, чтобы FCM не понижал приоритет доставки.

### 2. Пробуждение iPhone

На iOS используется только Apple VoIP push через PushKit и системный CallKit. Собственного фонового постоянного соединения на iOS нет.

iOS-сборка выполняется через Expo EAS Build. Это решение действует при условии, что APNs доступны из Туркменистана; это проверяется канарейкой через `apns_reach`.

### 3. Собственное сигнальное соединение

Клиент отправляет ping раз в 4–5 минут; окончательный интервал будет выбран по данным канарейки из Туркменистана.

Для heartbeat-соединений клиент передаёт серверу `disconnectAfterSec`, равный 2,5 интервала ping. Сервер закрывает соединение, если не получил очередной heartbeat за это время, и записывает причину `silence_timeout`. При смене сети и пробуждении после push клиент немедленно переподключается.

### 4. Сообщения и синхронизация

- `id` сообщения создаётся на телефоне.
- Неотправленные сообщения хранятся в локальной SQLite-очереди.
- Повтор отправки продолжается до подтверждения сервера, всегда с тем же `id`.
- Сервер дедуплицирует сообщения и не создаёт повторов.
- В каждом чате есть сквозной порядковый номер.
- При каждом подключении и при обработке push клиент догружает все сообщения после последнего полученного номера.

### 5. Статусы сообщения

Последовательность статусов:

1. часы — сообщение в локальной очереди;
2. ✓ — сервер принял сообщение;
3. ✓✓ — устройство получателя подтвердило получение;
4. прочитано — пользователь открыл сообщение.

### 6. Звонки

Приглашение звонка идёт одновременно по push и по существующему соединению.

- Android: системное полноэкранное уведомление CallStyle и foreground-служба типа `phoneCall`.
- iOS: CallKit.
- Звонок ожидает ответа 45 секунд, затем создаётся сообщение о пропущенном звонке.
- При смене сети выполняется ICE restart.
- При кратком обрыве до 5 секунд вызов ожидает восстановление и не сбрасывается.
- Потеря сигнального WebSocket не должна разрывать уже идущие аудио и видео.

## Последствия

- Требуется серверная дедупликация по идентификатору и подтверждения доставки.
- Android использует foreground-службу и постоянное тихое уведомление как резервный/параллельный канал.
- iOS не использует постоянный фоновой сокет; доступность APNs становится критической предпосылкой.
- До начала production-реализации нужны результаты Canary по доступности сервисов, UDP и стабильности heartbeat.
