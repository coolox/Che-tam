# ADR-001: доставка сообщений и звонков в «Чё-Там» (только Android)

- **Статус:** принято
- **Дата:** 2026-10-01
- **Область:** Android; доставка сообщений, пробуждение приложения и сигнализация звонков.

## Контекст

Канарейка в мобильной сети показала: соединение без трафика умирает за 9–15 минут, с ping раз в 1–9 минут живёт. У родственников Android с Google (Xiaomi/Samsung). Постоянное уведомление на Android допустимо, но не должно быть режимом по умолчанию.

Нужно обеспечить доставку сообщений и звонков в условиях нестабильной/ограниченной сети, не создавая дублей и не расходуя батарею постоянным соединением без необходимости.

iPhone и iOS-доставка отложены до отдельного архитектурного решения и не входят в этот ADR.

## Решение

### 1. Пробуждение Android по умолчанию

По умолчанию используется только срочный FCM push высокого приоритета. Постоянного WebSocket-соединения и постоянного уведомления в штатном режиме нет.

На каждый срочный push показывается видимое уведомление о сообщении или звонке; иначе FCM может понизить приоритет доставки.

### 2. Запасной режим Android

Собственное WebSocket-соединение в foreground-службе с тихим постоянным уведомлением «Чё-Там на связи» — это запасной режим.

Он включается автоматически только если сервер фиксирует, что FCM push не дошёл. В запасном режиме сообщение и приглашение звонка могут идти по push и по соединению одновременно. Дубликаты устраняются по стабильному `id`.

### 3. Собственное сигнальное соединение

В запасном режиме клиент отправляет ping раз в 4–5 минут; окончательный интервал выбирается по данным канарейки из Туркменистана.

Для `ws_heartbeat` клиент передаёт серверу `disconnectAfterSec`, равный 2,5 интервала ping. Сервер закрывает соединение, если не получил очередной heartbeat за это время, и пишет `canary_ws_close` с причиной `silence_timeout`.

При смене сети и при пробуждении от push клиент немедленно переподключается. Для `ws_keepalive` таймер тишины не включается.

### 4. Сообщения и синхронизация

- `id` сообщения создаётся на телефоне.
- Неотправленные сообщения хранятся в локальной SQLite-очереди.
- Повтор отправки продолжается до подтверждения сервера, всегда с тем же `id`.
- Сервер дедуплицирует сообщения и не создаёт повторов.
- В каждом чате есть сквозной порядковый номер.
- При каждом подключении и при обработке push клиент догружает все сообщения после последнего полученного номера.

### 5. Статусы сообщения

Последовательность статусов:

1. часы — сообщение в локальной очереди;
2. ✓ — сервер принял сообщение;
3. ✓✓ — телефон получателя подтвердил получение;
4. прочитано.

### 6. Звонки

Приглашение звонка идёт по FCM push, а при активном запасном соединении — одновременно по push и по соединению.

- Входящий экран — системный: полноэкранное уведомление CallStyle и foreground-служба типа `phoneCall`.
- Звонок ожидает ответа 45 секунд, затем создаётся сообщение о пропущенном звонке.
- При смене сети выполняется ICE restart.
- При кратковременном обрыве до 5 секунд звонок ждёт восстановление и не сбрасывается.
- Потеря сигнального WebSocket не должна разрывать уже идущие аудио и видео.

## Последствия

- Нужны серверная дедупликация по идентификатору и подтверждения доставки.
- Нужен серверный способ определить недоставку FCM push и автоматически включить/выключить запасной режим.
- В обычном режиме Android не держит постоянный сокет и не показывает постоянное уведомление.
- iPhone, APNs, PushKit, CallKit и iOS-сборка намеренно отложены.
- До production-реализации нужны полевые результаты Canary по FCM, стабильности heartbeat, доступности сервисов и причине обрывов около одного часа.
