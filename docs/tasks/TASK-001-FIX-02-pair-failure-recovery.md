## Blocking defect

`getScheduleState()` currently takes the latest individual failed record as `lastFailedAttemptUtc`. Each probe produces two records. If HTTPS succeeds but WebSocket fails, the resulting partial pair is treated as a failure that enables 10-minute recovery. The next hourly probe produces another individual WSS failure, resetting the recovery window forever. This defeats the adaptive traffic policy.

## Required behavior

- A **failed pair** means both records from one probe attempt failed.
- A **partial pair** (HTTPS success + WSS failure, or inverse) must remain in hourly cadence after the initial 24-hour window. It is valuable diagnostic data but not a reason to create a persistent high-traffic loop.
- A completely failed pair enters 10-minute recovery for 60 minutes.
- After 60 minutes with no later fully failed pair, cadence returns to hourly.
- Group records into pairs deterministically without adding personal data. The two records generated by one `runConnectivityCheck` already have nearly identical timestamps and fixed test types; if a small internal grouping marker is necessary, it may be added only as a non-identifying local journal field and must be documented.
